## 3. Additive persistence and durable state

Use the existing dedicated Postgres cluster with new `backoffice.office_*` tables. Prefer explicit columns/checks and validated JSON for bounded flexible data. UUID IDs, foreign keys, UTC timestamps, optimistic versions, indexes and unique idempotency keys are required. Store money/cost in defined exact units with currency, never floating point. Proposed minimum:

| Table | Durable content |
|---|---|
| `office_agents` + profile versions | Stable slug/name, role, approved brief/version, portrait, enabled/paused, tool-policy ID, configured model alias. No human login email or commission fields. |
| `office_workspaces`, `office_workspace_grants` | Client/project reference, environment, canonical allowed root, permitted repos/domains, data/tool scopes and agent grants. Use an explicit internal-workspace scope for internal work, rather than leaking a real client context. A nullable database client foreign key is allowed for this scope; transport carries a stable internal scope ID. Do not reuse client account ownership as agent authorization. |
| `office_tasks`, `office_task_dependencies` | Goal, initiating owner, project/workspace, assigned agent, parent/dependencies, priority, schedule, state, input/artifact references, version and submit idempotency key. |
| `office_runs`, `office_run_steps` | Task/agent/profile/policy versions; attempt/state, bounded execution budget, provider request references, usage, worker lease/heartbeat, checkpoint and cancellation. Each tool step has canonical arguments hash, stable operation key, state and result/error reference. |
| `office_approvals` | Exact proposed operation, scope/target, payload hash, current-record version, expiry, canonical proposed/pending/approved/rejected/expired/superseded/cancelled state plus separate one-time consumption metadata, requesting run and deciding owner. Approval and one-time consumption use compare-and-set transactions; consumption belongs to the tool-operation ledger/consumed-at metadata, not a new approval enum. The initial pilot only accepts an internal package. |
| `office_events`, `office_artifacts` | Append-only replayable events with task/run/workspace IDs, per-workspace monotonic sequence and sanitized payload; private artifact key/hash/type/size/version, producer and scope. |
| `office_schedules`, `office_dispatch`, `office_tool_operations` | Durable next execution/unique schedule occurrence, retry/backoff/lease records and external-effect reconciliation ledger. Enforce uniqueness for each scheduled occurrence and logical side effect. |

Canonical state contracts are defined in `data/response-presets.json` and `specs/product-and-presets.md`; do not create a second abbreviated state machine. Task states: `draft`, `queued`, `assigned`, `in_progress`, `waiting_for_input`, `waiting_for_review`, `changes_requested`, `review_passed`, `waiting_for_owner_approval`, `completed`, `pause_requested`, `paused`, `blocked`, `failed`, `cancel_requested`, `cancelled`. Run states: `queued`, `starting`, `running`, `waiting_for_tool`, `pause_requested`, `paused`, `cancel_requested`, `cancelled`, `succeeded`, `failed`, `interrupted`. A task can have multiple immutable run/attempt records. Worker lease, retry timing, heartbeat and fencing are metadata; they are not additional task/run enum values. A step waiting for owner input/approval releases worker capacity; preserve its checkpoint and put the business task into the appropriate waiting state without repeating completed effects. State changes and emitted events commit together. Cancellation requests are distinct from confirmed cancellation and cannot retract completed external effects.

Persist delegation and dependencies; a supervisor creates a child task rather than making an unrecorded in-memory call. Profiles can number seven, twenty or more without spawning that many concurrent paid requests. Start with a small configurable concurrency limit and enforce per-run/global budget reservations atomically. Missing model credentials/configuration produces `blocked: configuration_required`, never pretend activity or silently borrow website credentials.

Do not reuse the existing invoice outbox for generic office work: invoice void/status code processes entries by invoice aggregate ID. Use the separate office dispatch table so office retries cannot accidentally send invoices. The current invoice outbox is a useful transaction/idempotency pattern, not an implemented general office worker.

## 4. Worker, event delivery and workspace execution

Add a proposed independent `apps/office-worker` process, excluded from public Vercel uploads. It shares typed contracts and a narrow audited persistence layer, not browser components or Next request/session APIs. Existing DB/env modules import `server-only`; do not import those directly into an ordinary Node worker or strip protections globally. Extract small runtime-neutral contracts/adapters or provide a worker-specific adapter. Keep provider/tool credentials only in server processes and only configure those explicitly supplied by the owner.

The worker claims ready dispatch records transactionally with row locking/skip-locked, bounded leases and fencing tokens; commits the lease, then performs network/model work outside the DB transaction. Heartbeats extend valid leases. Each result/checkpoint requires the current lease token so an expired worker cannot overwrite its replacement. Startup reclaims expired leases, applies bounded backoff and exposes exhausted retries for review. A model request interrupted before its response may consume usage; reconcile known request IDs where supported and do not claim exactly-once model execution.

External effects require a separate tool ledger and stable provider idempotency key where supported. For an ambiguous send/deploy timeout, reconcile or mark `unknown_outcome` for review; never blindly retry an effect. Approvals are for the exact current payload/scope, expire, and are invalidated by changes. Revalidate owner authorization, tool scope, versions, cancellation and approval immediately before execution. Agent prose saying "approved" has no authority.

Browser → server mutation commits task + event + dispatch → worker advances persisted steps → office event feed updates the browser. Use authenticated same-origin SSE with `Last-Event-ID` or polling fallback; replay from Postgres after reconnect and deduplicate sequence IDs. Scope queries before replay, including artifact downloads. Events contain milestones and summaries, not tokens, secrets or private reasoning. Bound replay batches, handle gaps with a refreshed snapshot, use keepalives and reauthenticate/reconnect on session expiry. `LISTEN/NOTIFY` can wake a worker but is not the durable queue. Existing CSP permits same-origin connections; no broad CSP relaxation is required. A disconnected browser does not cancel a queued job.

The Windows scripts currently launch the backoffice/database and register an **interactive, current-user logon task**, not a continuously verified boot service. Add separate worker build/start/install documentation and hidden, limited-privilege supervision, health/heartbeat and structured rotated logs. Reuse the dedicated cluster without reinitializing it. Do not modify the existing task, shared tunnel or production services during development. Production activation needs an agreed restart/check/rollback window. Browser closed can work while the PC, network, database and worker remain available; computer asleep/off cannot execute jobs. On recovery, persisted work resumes. True availability before logon or while the workstation is off requires an approved service/always-on host arrangement; record this limitation openly.

**Sam and Theo execution boundary:** each client project gets a canonical registered workspace; each task gets its own branch/worktree or isolated checkout, executor lease, authorized file/domain/tool allowlist and cleanup owner. They cannot execute inside `D:\Enztronic` or a shared deployment checkout by default. Never derive workspace paths from arbitrary agent text. Resolve/check absolute paths, junctions/symlinks and Git boundaries before every filesystem operation. Worktrees prevent edit collisions but are not security sandboxes: run commands through a constrained executor with appropriate OS isolation/ACLs, resource limits, timeout and network policy. Do not offer a broad shell that can read the host home, other client roots, credential stores or office database/model secrets. Run untrusted project install/build scripts with a scrubbed environment and no production secrets. If isolation is unavailable, disable command execution and expose drafts/plans only.

Return changed-file manifest, diff/commit, test results, review notes and preview/artifact references. Never merge, deploy, push, publish or perform outbound client communication merely because a run finished; use the approved capability policy and explicit owner approval for its exact effect. Cleanup releases only that task's owned lease/worktree after checking paths and retaining reviewable artifacts. Preserve unrelated dirty/untracked files. Repository content, web pages and imported documents are untrusted task data, not authority to widen tools or bypass approvals.

Apply approved additive migration against the dedicated cluster, deploy backoffice/worker deliberately, then verify signed-in and denied routes, loopback binding, health and one harmless task. Report remaining unconfigured integrations.

Rollback: disable new submissions/schedules, fence/pause workers, reconcile in-flight effects, revert office code/UI to the prior build and preserve office tables/events/artifacts. Additive schema should remain compatible; do not drop tables or edit migration checksums for routine rollback. Restore a database backup only under a separate reviewed recovery plan, because restoring an older financial database could lose valid later invoices/payments. Never roll back by broadly stopping `cloudflared` or deleting the dedicated database.

Minimum owner inputs before dependent live actions: actual approved model/provider connection and spend caps; approved client/repository roots and task boundaries; exact send/deploy/financial approval policy; production availability target and permitted host/startup arrangement. Securely configure credentials through existing local setup, never by asking to paste them into chat. Local UI, schema, queue, fake adapters, regression tests and review artifacts can proceed without these live inputs.
